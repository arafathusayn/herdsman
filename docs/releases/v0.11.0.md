# herdsman v0.11.0

This release makes herdr-core the default execution backend for new installations and config files. Existing installations retain their recorded choice. The native Herdr app is required for visibility; the legacy TUI backend and an optional core-to-TUI attachment remain available.

## herdr-core by default

herdr-core is Herdr's terminal server, and herdr-app is the native app where a person sees its terminals. On this backend herdsman starts each agent in a core terminal, identifies it by its process (PID, start time and a generation), never by an address or a name, and reaches it through notices it waits for, with nothing typed into its terminal by automation.

New installations need no backend opt-in. To select core explicitly on an existing installation:

```toml
[runtime]
backend = "herdr-core"
```

`herdsman up --backend herdr-core` selects it for one new route. The former `[runtime.core] experimental` key is accepted without effect. Existing routes retain their backend; no automatic fallback changes it.

The other keys of `[runtime.core]` and `[runtime.app]` are read:

| Key | Default | What it does |
| --- | --- | --- |
| `[runtime.core] socket` | unset | The core's absolute socket |
| `[runtime.core] session` | `default` | The core session, resolved under hc's path rules when no socket is set. A socket and a session that name different endpoints stop the run with both named |
| `[runtime.core] binary` | `hc` | The hc program `herdsman doctor` runs, against the resolved socket |
| `[runtime.core] connect_timeout` | `5s` | How long a connection to core may take to answer |
| `[runtime.core] ready_timeout` | `90s` | How long an agent may take to become ready after it registers |
| `[runtime.app] binary` | `herdr-app` | The app program |
| `[runtime.app] home` | the user's main app | An absolute app home. The app's binding to core is verified per home, so a new home is verified again before an agent is dispatched |
| `[runtime.app] visibility_timeout` | `15s` | How long to wait for an agent to appear in the app |

A new route resolves its endpoint once and keeps it: the launch steps journal the socket, session and hc program, and each execution record the id of the core it reached. A config that later names another endpoint for that route is refused with `backend_migration_required`; one that names none keeps the route's endpoint. `HC_SOCKET`, `HC_SESSION` and `HC_TERMINAL_ID` in the daemon's environment never choose a route's endpoint, so a daemon started under an agent does not take that agent's core. The timeouts and the app are read from the config for each launch. A duration that does not parse or is not positive, a relative socket or app home, and a session that is not one path segment stop every run with `invalid_runtime_config`, on either backend. `herdsman runtime doctor` reports each value in use and where it came from.

The optional TUI view is enabled with an explicit endpoint:

```toml
[runtime.tui_view]
enabled = true
socket = "/absolute/path/to/herdr.sock"
```

The view attaches to the existing core execution in a dedicated workspace. It uses expiring display metadata, not native TUI agent identity. Moving the pane preserves its binding. Closing or detaching it never stops core, and `runtime show` can reattach it. TUI failure does not block execution or native-app visibility.

## Compatible versions

| Component | Version | What happens with another one |
| --- | --- | --- |
| herdr-core | `0.1.20`, tested | Another version at protocol generation 1 runs; `runtime doctor` warns that it is untested |
| Core protocol generation | `1`, the one pinned generation | A core at another generation is refused at hello with `unsupported_generation`: update herdsman or herdr-core |
| herdr-app | `0.1.15`, tested; `0.1.14` the oldest supported | An older app, or one that lacks a command herdsman runs, is refused as unavailable |

Every core method herdsman calls is listed in one file, `internal/hc/methods.go`, and the methods core announces at hello are checked against that list before any call. CI runs against a fake core at the pinned generation.

## Platforms

herdr-core and herdr-app are claimed for macOS on Apple silicon only. On any other machine `runtime doctor` says why in its `app-support` check, fails it when core is selected, and names `backend = "herdr-tui"`. The Linux acceptance run skips the core gates by name, and on an Intel Mac the core probes of the acceptance suite fail with that reason.

## Harness levels

| Harness | Level on core | What a person does |
| --- | --- | --- |
| Claude Code 2.1.322 | Unattended after initial start | Nothing after the start line: the agent holds `herdsman notice wait` as a background command and is woken by each notice with nothing typed |
| Codex 0.164.0 | Attended | Submit the initial start line and handle interruptions or paused goals. Later notice wakes use the verified native conversation queue. A pause holds new work and lets the turn end |

`herdsman up` prints these steps for each agent before the route starts, and `herdsman runtime doctor` reports each harness with the same level and the same steps.

On core no automation types into a terminal. An agent pulls its instructions with `herdsman notice wait`, `notice read` and `notice ack`, through a second daemon socket, the worker socket, that serves only the calling execution's notices. A line typed through `herdsman runtime submit` or the web route page is a person's action: it asks for confirmation, is refused from inside an agent, and is recorded with its outcome. From the browser, the process checked as the person's terminal is the `herdsman web` server, so only a server started from a person's terminal can type. Neither a typed submit nor another agent's screen text is served as an MCP tool.

## Stop, and the window that remains

Stop asks each agent for its final report by notice, then stops each execution through core. Immediately before `terminal.kill` it checks that the address still holds the recorded process. `terminal.kill` takes an address only, so one window remains between that check and the kill: a recovery shell that core started at the same address in those seconds. Recovery shells are otherwise never killed by herdsman: they stay until a person closes them.

## Conversations, cards and checkpoints on core

- After an agent registers, herdsman records the harness's own conversation id with where it was read: for Claude Code its project transcript for the agent's working folder, for Codex its rollout's session record. Only those two folders are read, only a session written since registration whose recorded folder is the agent's counts, and when two sessions of one folder qualify, only a notice id issued to that agent and printed in its transcript settles which is its own. Otherwise nothing is recorded, and the checkpointer, which finds the transcript from this record, says there is no evidence rather than guess.
- The card watch reads each agent's screen through the runtime. A side-agent card is relayed once to the adjutant as side-agent data from the orchestrator. Too many cards, a full side-agent budget, a refused relay, a failed read, a lost agent and a dialog seen twice are alerts: the route's status lists each, one `needs_attention` event announces it, and it is resolved when its cause is gone.

## Upgrade and rollback

The account store moves to schema 7 and each route store to schema 3: the installation default backend, execution records with the experiment that wrote them, notices and typed submits. On an existing store the migration only adds; the one value it writes into an existing row is the experiment label of a herdr-core execution record. An older herdsman refuses the migrated store with `ErrSchemaNewer`, so going back to the Herdr TUI is the configuration line `backend = "herdr-tui"` on this version, not a downgrade. Existing installations retain their stored backend; new installations select herdr-core.

## Harness behavior

The implementation makes these choices explicit:

| Capability | Behavior in this release |
| --- | --- |
| Pass the start line as the harness's initial prompt, an added launch argument that the compatibility contract would need an exception for | No argument is added. `up` stops at `needs_attention` with the line, and a person types it in the agent's pane at each start |
| Wake Codex through its own message queue | A fixed line is queued to a proven local conversation; interruptions and paused goals remain attended |
| Restricted Codex on core | Codex 0.164.0 uses a fresh permissions profile with `network_proxy`; only the exact worker socket is allowed |
| Set `keep` to false after adoption | `keep` stays on: a finished agent terminal stays in core until a person closes it |

## Also in this release

- `herdsman status` and the web route page show each execution of a route by its backend, with its process, readiness, attention reasons, open notices and unresolved typed lines. `herdsman runtime show` brings an execution's terminal forward in the app.
- `herdsman runtime doctor` covers each `[runtime.core]`, `[runtime.app]` and `[runtime.tui_view]` value in use with its source, the core endpoint and version, the app binding, the launch and core environments, repository access, the inventory, the notice channel, each harness and route attendance.
- `herdsman delete` now also makes the daemon forget the route's channel once the inbox is removed, on both backends; before, a route whose inbox the daemon held stayed listed after its files were gone. On core, pause holds and resume lifts each agent's channel, and delete snapshots and removes the route's inbox. `herdsman undo` of a route's delete registers that channel again at the inbox it puts back, and leaves the route stopped rather than deleted: its agents ended with the delete, and `herdsman resume` starts them again as new executions under fresh launches.
- The `up` form in the terminal UI has a backend field, prefilled with what `up` would choose.
- Automations hear runtime events as `runtime.<kind>`, such as `runtime.needs_attention`, delivered at most once. The `route pause` built-in pauses a core route through its pause verb and types nothing.
- A route's trace records core launch steps, notice issue, claim and handling, and typed lines as spans, by id and never by content.
- `make bench-up` measures `up` on core against a fake core world, with the A/A control, as a 95% confidence interval.

## Review fixes

Task continuation is committed atomically with acknowledgement, including while held and at maximum payload size. Final reports take precedence over ordinary open claims; repeated claims recheck authorization and deadlines. Stopped tasks restart with a fresh execution identity. Task commands preserve quoting and preludes. Registration persists its launch guard, process evidence, creation time and effective policy/argv digests.

Restricted Codex workers use a fresh permissions profile and the network proxy, allowing only their worker socket. Real sandbox checks cover filesystem grants, denied control/core sockets, denied direct TCP, and broader inherited configuration. Restricted coordinator pairs use the manual confirmation flow.
