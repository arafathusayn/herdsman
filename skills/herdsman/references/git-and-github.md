# Git, worktrees and GitHub

## Identity and credentials

- Never change git identity, remotes or global config in any pane. The one-shot credential helper is the only way to authenticate a push or fetch:
  `git -c credential.helper= -c credential.helper='!f() { echo username=<gh account>; echo password=$(gh auth token --user <gh account>); }; f' <fetch|pull|push ...>`
- `-c credential.helper=...` adds to the configured helpers, and a helper that is already configured (for example `gh auth git-credential` for the active account) answers first: the push then runs as the wrong account and fails with 403. Put an empty `-c credential.helper=` before the one-shot helper to clear the list for that command only.
- Never switch machine-wide CLI state (`gh auth switch`, a CLI's linked project folder): every session on the machine shares it. Pass the account per command. Before you trust an empty result or a "not found", check which account, key or workspace the call used.
- `gh` with a non-default account: `GH_TOKEN=$(gh auth token --user <gh account>) gh ...` inline on every call. The default account may not see the organisation at all ("Could not resolve to a Repository").
- GitHub handles are names: keep them out of run-state files and pull-request bodies (roles or issue numbers instead).
- A `git push` that hangs with no progress while `gh` works can come from a resolved address that connects but never answers. Compare `curl -s -m 8 -o /dev/null -w '%{http_code} %{remote_ip}' https://github.com/` with the same call plus `--resolve github.com:443:<other address>` (from `dig +short github.com`). Fix it per command, with no config change: `git -c http.curloptResolve=github.com:443:<address> ...`. Give pushes `GIT_HTTP_LOW_SPEED_LIMIT=1000 GIT_HTTP_LOW_SPEED_TIME=20` so that a stall fails fast instead of holding an agent for minutes. Tell every agent that pushes.
- `gh pr view --jq` takes one argument only; `--arg` fails, and a waiter that swallows the error loops on nothing. Put values into the jq text, or pipe `gh api ...` into `jq --arg`. Read a new waiter's output after its first poll.

## Worktrees (optional per route)

- One worktree per task, lettered, under a git-ignored `worktrees/` folder next to the clone: `git -C <clone> worktree add <worktrees>/<x> -b <branch> origin/<base>`.
- Fetch before branching; the local base branch is usually behind `origin/<base>`.
- Never switch branches, reset or stash in the user's live checkout. A clean status says nothing about edits that are about to start there, and other sessions can share the checkout. Branch work happens in worktrees (ask before creating one when the user requires it).
- A fresh worktree has no ignored files: copy only the `.env` files the gates need, read them for live endpoints first (a runtime that loads `.env` files can point tests at real data), and run a frozen-lockfile install before any gate. Check that the tests import the worktree's own code, not another checkout's. Keep paths short where a throwaway database puts a Unix socket. A worktree that holds copied secrets is removed at route close, with the user's go.
- Existing worktrees on the target branch may be reused if clean; say which letters are free in the contract, or an implementer picks one that a sibling expects.
- Reviewer worktree: detached (`--detach origin/<base>`), then `git checkout --detach origin/<head>` per review.
- Stacked work that has no review yet rebases onto the sibling branch inside the same repository (`git rebase <sibling>` works across worktrees). A reviewed branch takes updates with a merge ([`ownership-and-integration.md`](ownership-and-integration.md), Numbers and stacks).
- Migration numbering collides across open pull requests; the shared rules must state the next free number and which open branches already use the following ones.

## No-commit routes (unborn branch, "no commit until done")

- No worktrees (they need a commit). Review units are tree snapshots taken with a temporary index: `cp .git/index <scratch>/snap.index && GIT_INDEX_FILE=<scratch>/snap.index git add -A && GIT_INDEX_FILE=<scratch>/snap.index git write-tree`; review with `git diff <before> <after>`; prove the user's index is untouched with `git diff --cached --quiet <S0 tree>`.
- Baseline copy: `git checkout-index -a --prefix=../<name>-baseline/`. Parallel work: APFS clones (`cp -cR`), ported back with `git apply --3way` on a temp index. Only on disjoint files; a whole-repo rename in one tree makes a parallel clone a duplicate.
- A hand-run `git add -A` after re-init drops ignored-but-tracked files; list them and `git add -f` them in the final commit.
- Implementers: no git command that writes, `mv` not `git mv`, throwaway `HOME`.

## Pull requests

- READY pull requests, not drafts, when the user said so. `gh pr create --repo <org>/<repo> --base <base> --head <branch> --title ... --body-file <file>`.
- Body rules (user's standard): Summary, per-file bullets with why, Verification with exact commands and databases, Known gaps. No reviewer or tool names, no people, no metrics, no process history. Grep the body for banned words before creating.
- Under a "CI green before the body" rule: open the pull request with a minimal body, wait for CI, then the integrator writes, checks and pushes the full body.
- Before a body edit, save the live body and look for bot-appended blocks (`<!--`, "Summary by"). After `gh pr edit --body-file`, read the body back and `diff` it with the file: GitHub strips the final newline, so one differing last line is a match, anything more is not.
- Before the user sees a reply draft that cites commits, check that each one is on the pushed head: `git merge-base --is-ancestor <sha> <head>`.
- A `pull_request` run tests the merge of the head with the current base (`actions/checkout` fetches `refs/pull/<n>/merge`), not the head alone; the run still lists the head commit. When the base moved after the branch was cut, read the run log for the merge commit it checked out and that commit's parents before you claim that CI missed the base. A check that is not in CI (a local smoke test) still needs a run on the merged result: put it in the pull request's Before merge list.
- Landing-order gates ("update after PR n merges") are Known-gap lines, not defects, so the pull request can open.
- "Green" means that every expected check ran on the head, not only that none failed or pends. A repository with no checks has no green: say that, and name the local gates that ran instead. A base change does not start `pull_request` workflows, so a push made just before a base change can leave the head with no CI at all; a ruleset that requires no status checks then lets it merge. Compare the check names with the expected list (or read the runs for the head commit); a new push, or closing and reopening the pull request, starts them. Tell authors: change the base first, then push. When the user's instruction is "approve when green", apply it as GitHub shows it, then name the missing runs in one line.
- A finding only about the pull-request body (process history, a sentence about a change the base never had) needs no implementer round: the orchestrator edits the body on the user's go, and the reviewer checks the body only. The head and the bot approval stay valid.
- `statusCheckRollup` keeps runs that a newer push cancelled next to the newer runs of the same name. Group by name and take the newest start time before you call a check failed.
- Stacked pull requests open with `--base <sibling branch>`; CI still runs against the workflow of the default branch, so a failing check may come from the base.
- GitHub native stacks (`repos/O/R/stacks`, no preview header needed):
  - Create, bottom to top: `printf '{"pull_requests":[101,102]}' | gh api -X POST repos/O/R/stacks --input -` (integers, 2 to 100; each base ref must equal the previous head ref; same repository). The answer carries the stack `number`.
  - Append on top: `printf '{"pull_requests":[103]}' | gh api -X POST repos/O/R/stacks/<stack>/add --input -` (the first new base ref must equal the current top's head ref).
  - Find a pull request's stack: `gh api repos/O/R/stacks --paginate --jq '.[] | select(any(.pull_requests[]; .number==<n>)) | .number'`; read one with `gh api repos/O/R/stacks/<stack>`.
  - Unstack: `gh api -X POST repos/O/R/stacks/<stack>/unstack` removes every unmerged pull request it can (queued ones stay); 200 returns the rest, 204 means the stack is gone, 409 means another request is changing it.
  - Creating, extending or dissolving a stack, and retargeting a base, are GitHub mutations that need the user's go unless the task file grants them.

## Review bots (Pullfrog seen)

- Reviews arrive within minutes of a push. Loop: fetch review body and inline comments, verify the claim, test-first fix, push, reply on the thread via `gh api repos/O/R/pulls/<n>/comments/<id>/replies` with "Addressed in <sha>".
- "No new issues found" in a review body means clean; the approval check flips to pass only then. The approval check attaches to the reviewed commit and never clears on thread resolution alone; post an issue comment mentioning the bot and asking for a fresh review of the current head. The mention starts a workflow run; wait on that run, then read the new reviews and the open threads.
- The bot does not always post a clean review on the newest head; it can answer only in threads ("Addressed in <sha>"). The approval signal on the current head is: the newest run of the approval check is SUCCESS, no unresolved thread, and the newest run of every CI check is green. Read the head again right before you post an approval, and pin the approval to that commit. An approval is not a merge: an author push after it needs a new approval when the rules require approval of the last push.
- When the bot has not reviewed the current head (a failed run, a usage or billing stop), say so and offer to wait for its run before the first merge. Merge without it only when the user confirms with that knowledge: a bot that comes back can find real issues in pull requests that already merged.
- Agents often end a fix round before the bot approves. Fix prompts say: wait until the approval check is SUCCESS on the new head, then write the report. An agent that waits on the bot for a head that already conflicts wastes a bot run: interrupt it and send the update round (a merge of the default branch) first.
- Before you post found issues on a pull request, compare each bot review's inline comments with the open threads and read the review body for findings outside the diff. Post only what is missing; duplicate comments add noise to the author's threads.
- The bot keeps finding the next layer on concurrency and object-store code; design two-phase claims with unique tokens up front, no store I/O inside a database transaction, and race tests that are shown to fail on the old code and synchronise with barriers, not sleeps.
- Review rounds, not coding, take most of the time from implementation to an open green pull request.
- GitHub Actions can stop for the whole organization on a billing failure ("The job was not started because recent account payments have failed or your spending limit needs to be increased"); every job and the review bot then fail within seconds of scheduling. Only the organization owner fixes it; a re-run of a failed run is the cheapest probe. The local review stays valid; merging without CI is the user's call.
- Pullfrog runs on the same model account as the Codex implementers; it is a third-party bot, not a GitHub feature. When that account's usage limit is reached, Pullfrog's reviews and its approval check fail as well, so a merge gate that needs the bot cannot pass until the reset. Tell the user; the merge decision without the bot is theirs.

## Merges

Merges are the user's unless the interview (or a later instruction) authorizes the orchestrator. An authorized form: "Merge the PRs when both the local review and the bot reviewer on GH approve them. Use squash and merge technique."

- Gate, on the SAME head commit: latest `review-<pr>-<n>.md` says `VERDICT: pass`; the bot approval check is SUCCESS; every CI check green; `mergeable: MERGEABLE`. A push after the review invalidates the pass.
- Command: the asynchronous merge REST API, the only merge path that handles native stacks and merge queues (`gh pr merge` cannot merge a stacked pull request: "must be merged using the asynchronous merge REST API"). Read the repo's merge settings first (`gh api repos/<org>/<repo> --jq '{allow_squash_merge,delete_branch_on_merge,squash_merge_commit_title,squash_merge_commit_message}'`); pass title and message explicitly when the defaults would concatenate commit messages. Read the base branch's rules too (`gh api repos/<org>/<repo>/rules/branches/<base> --jq '.[].type'`): a `merge_queue` entry means the branch requires the queue. Then request the merge, pinned to the reviewed head. Without a required queue:
  `GH_TOKEN=$(gh auth token --user <account>) gh api -X PUT repos/<org>/<repo>/pulls/<n>/merge-async -f merge_method=squash -f merge_action=direct_merge -f sha=<reviewed head> -f commit_title="<pr title> (#<n>)" -F commit_message=@<pr body file> --jq '{status, details}'`
  With a required queue, use `-f merge_action=merge_queue` and drop `merge_method`, `commit_title` and `commit_message` (the queue's own merge method applies). Read that method first: `gh api repos/<org>/<repo>/rules/branches/<base> --jq '.[] | select(.type=="merge_queue") | .parameters.merge_method'`. When it is not the method the user authorized (for example `MERGE` or `REBASE` under a squash-only authorization), do not enqueue: ask the user.: `GH_TOKEN=$(gh auth token --user <account>) gh api -X PUT repos/<org>/<repo>/pulls/<n>/merge-async -f merge_action=merge_queue -f sha=<reviewed head> --jq '{status, details}'`. A direct merge past a required queue is a bypass and needs the user's answer like any other.
  - Keep the whole `details` object: the 409 check below needs its options, and an immediate `merged` answer carries the merge commit in `details.sha`. On a 409 or 400 `gh api` exits 1 and prints the raw body without the `--jq` filter; read that body, not only the exit code.
  - Answers: 202 `pending` with a `uuid`; 200 when already `merged` (with the merge commit sha) or already `enqueued`; 409 when a request for this pull request is already pending: its answer names that request's uuid and options, which may differ from yours. Adopt that uuid only when `expected_head_sha` is the reviewed head and `merge_method`, `merge_action` and `bypass_rules` match what the user authorized; otherwise do not poll it as this merge and do not send another request: stop and show the user the pending request; 400 `failed` for basic state (closed, draft). Rulesets and branch protection are checked later, in the background, so a 202 is not a merge.
  - Poll with the Monitor tool, never a sleep loop, with the same account: `GH_TOKEN=$(gh auth token --user <account>) gh api repos/<org>/<repo>/pulls/<n>/merge-async/<uuid> --jq '{status, details}'` until a final status: `merged` (`.details.sha` is the merge commit), `enqueued`, or `failed` (`.details.message` says why). Stop polling the uuid on any of the three. A push to the head after the request cancels the merge; that is the `sha` pin working. A uuid expires 24 hours after its last update (404).
  - `merge_action`: `direct_merge` merges now; `merge_queue` adds to the base branch's merge queue; `default` (or omitted) picks the queue when one is configured. `commit_title`, `commit_message` and `merge_method` apply to direct merges only. `enqueued` is final for this API and does NOT mean merged: confirm the merge in a second stage with `GH_TOKEN=$(gh auth token --user <account>) gh api repos/<org>/<repo>/pulls/<n>/merge` (204 merged, 404 not yet) or `GH_TOKEN=$(gh auth token --user <account>) gh pr view <n> -R <org>/<repo> --json state,mergeCommit`.
  - Stacks: requesting the merge of a stacked pull request merges it together with every open pull request below it in the stack. Before you request the top one, list the pull requests below it (`gh api repos/<org>/<repo>/stacks/<stack> --jq '.pull_requests[] | select(.state=="open") | .number'`) and check each one: it is in the route's merge authorization (Scope below), and it passed the gate above on its own head. A pull request below outside the authorization goes to the user before any request. To land only the bottom part, request the merge of the highest pull request that passes both checks. When two pull requests in the stack carry migrations numbered from the same base, merge them one at a time: request the lower one, wait for `merged`, run the migration fix round on the next one (item 7 of the review loop in `SKILL.md`), and review its new head before its merge request.
  - `gh pr merge <n> --squash --subject ... --body-file ...` still works for a pull request outside any stack, but prefer the async call so one procedure covers every case.
- A ruleset on the base branch may require a second human approval after the last push (`gh api repos/<org>/<repo>/rules/branches/<base>`); pull requests authored by the user's own account cannot get it from that account, and `gh pr merge` answers "the base branch policy prohibits the merge". The same holds when the integrator pushed with the user's account to another author's pull request: the approval of the account that pushed last does not count. Ask the user: admin bypass, a colleague's approval, or a ruleset change. Never bypass without that answer. The bypass is `-F bypass_rules=true` on the merge-async call (it bypasses only the rules the token's account may bypass, and works for stacked pull requests, so unstacking is no longer needed for it); with `gh pr merge` it is `--admin`.
- Branch after merge: when the user says so ("Remove branch if it's safe"), delete the remote branch ONLY when the PR state is MERGED and `gh pr list --state open --base <branch>` is EMPTY. Deleting a branch that an open pull request targets makes GitHub CLOSE that pull request (GitHub does not retarget on an API ref delete). Recovery: recreate the ref at its last sha (`gh api -X POST repos/<o>/<r>/git/refs -f ref=refs/heads/<b> -f sha=<sha>`), `gh pr reopen <n>`, `gh pr edit <n> --base main`, then delete again. Correct order for a stack: retarget the dependents to main FIRST (`gh pr edit <dep> --base main`), then delete. Make the delete command gate on the dependent count in the same shell (`if [ "$dep" = "0" ]`), never print-and-delete. Keep local worktrees and branches until route close. Merge dependent pull requests in order; a pull request whose Known gaps say "update after PR n merges" gets that update from its implementer first.
- A merge while the pull request's implementer is in a fix round on it: tell the implementer at once to move the fix to a new branch from the new default branch. A push to a merged branch is lost.
- After a sibling lands, the other open pull requests on the same files get an update round: a merge of the default branch into the branch, not a rebase. The merge can add new defects (an import cycle, two changes that clash in meaning). The earlier review pass stands for the logic; the merge gets its own short review before the pull request's merge. Changes that merge without a conflict can still clash and leave no resolution to read, so the review covers what the merge brought in (`git diff <reviewed head> <merge commit>`) read against the branch's own changes (a caller the branch uses that was renamed or changed, a helper with new behavior, a new rule the branch's code breaks), the resolutions (`git show --remerge-diff <merge commit>`), and the suites of every package that either side touched.
- A chain of pull requests whose bases are sibling branches (not a native stack) merges bottom up: retarget each one to the default branch, approve it at its head, squash-merge it pinned to that head. After a squash below, an upper pull request that changes lines the lower one added conflicts with the default branch, because the default branch holds the squash commit while the upper branch holds the original commits. Prove it before the merge: `git merge-tree --write-tree --name-only origin/<default> <head>` (exit code 1 means conflicts). Fix each level after the squash below it: a merge commit on the upper branch with parents (head, default) and the tree of `git merge-tree --write-tree --merge-base=<old lower head> origin/<default> <head>`. Dry-run the whole chain in objects only (`git commit-tree`, no refs, no push) and check that the final tree equals the top head plus the default branch's own newer commits. Work one level at a time, because each squash makes a new commit on the default branch. Whoever pushes the update becomes the last pusher, which changes whose approval counts.
- Several independent pull requests that share files, to be merged in one order: simulate the squash merges in that order in a scratch clone first (a fresh directory). Per branch: `git merge --squash <branch>`; when it is clean, `git commit -m "sim <n>"`, so that the next branch merges onto the result and not onto the old default branch; when it conflicts, list the conflicting files for that pull request (`git diff --name-only --diff-filter=U`), then `git reset --hard` to the last simulated commit and go on with the next branch. Merge the clean ones; send a conflicting one back to its author with one line per conflicting hunk. Read each body for deploy prerequisites first when the default branch deploys on every push.
- Before a merge, find out what it triggers: a deploy on every push to the default branch, a job that runs on each deploy, a write to a shared database. Then the merge is a production action: post-merge steps (seeds, migrations, secrets that only a person can create) are blockers in the body, and after the merge you check that the deploy ran for that commit. Report "code live" and "data live" separately.
- Verify a squash merge in the default branch's log (`git log origin/<default>`), not by ancestry: the branch's own commits never appear there.
- Scope is the route's pull requests only. Older open pull requests without a local review are not covered; ask.
- After each merge: run-state line, memory, tell the user in the reply. Report the final table (number, branch, head, checks, verdict, merged commit).
