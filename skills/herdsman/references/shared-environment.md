# Shared machine and test stack

All agents of a route run on one machine and usually on one test database container. Their gates compete for CPU, memory and database state, so a route must share these on purpose.

## Contracts name the environment exactly

- Before you write test database names into contracts, read the project's test-reset guard (for example a required "test" in the name) and the settings its suites need. Otherwise each implementer invents its own names and values.
- Give each agent its own databases, named in its contract or prompt. Never let one agent touch another's database. Name throwaway databases, queues and ports from a full unique id, not a shortened time-based one: parallel runs then collide. A fixture never changes state that the whole cluster shares (a shared role's password). The same holds for another session that works in the same repository, test database or staging environment: agree first on file owners, migration and decision-record number ranges, and a separate test database for each session, because sessions that share a database or a file set corrupt each other's runs and overlapping deploys break a shared environment. For commits and shared files, see [`git-and-github.md`](git-and-github.md), Worktrees.
- Before launch, check the shared stack: the container runtime is up, the test database is healthy, the ports are free, and stacks left over from earlier routes are stopped or recorded. A test that fails only under a full-suite load is a collision or a flake until it passes alone.
- Probe a new harness before a route gives it database-backed tests: sandbox network and approval modes decide whether it can reach the container.

## Share the load

- Heavy checks (type check, lint, tests, formatter, build) run one at a time on the whole machine, not one per agent, single-threaded where the tool allows, under one machine-wide lock (the lock of [`scripts/run-check.sh`](../scripts/run-check.sh): `lockf` on macOS, `flock` on Linux). Reason: parallel checks from several agents can hang the user's machine. Write the exact single-thread forms into the shared rules and the reviewer contract (one test worker and no file parallelism, ESLint `--concurrency=off`, turbo `--concurrency=1`, a native compiler's own single-thread flags: read its `--help` first). Forbid ad hoc formatters when the repository has no formatter script, and forbid handing checks to subagents.
- Every contract names the route folder's `run-check.sh <command>`. The orchestrator writes that file before any contract names it, as a wrapper that sets the route's limits and runs the shipped [`scripts/run-check.sh`](../scripts/run-check.sh), and makes it executable:

```sh
#!/bin/bash
export HERDSMAN_LOAD_LIMIT=<idle load plus a margin> HERDSMAN_MIN_FREE=<free memory percent>
exec /bin/bash <skill>/scripts/run-check.sh "$@"
```

  When the project already has its own machine lock (for example one shared test database that two runs tear down), the wrapper keeps both: `exec /bin/bash <skill>/scripts/run-check.sh lockf -k -t <seconds> <project lock> "$@"`. The machine-wide lock and its load gate come first and the project lock second, always in that order, so no two holders wait on each other; anything outside the route that takes only the project lock still serializes with the route.

  The script takes the lock, then, inside the lock, waits while the 1-minute load average is at or over the limit or free memory is low, gives up with exit 75 after `HERDSMAN_GATE_WAIT` (default 10 minutes), lowers the check's priority by 10 and runs it. Wait inside the lock: a reading taken before the lock is out of date by the time the lock is free. Put every extra gate of the wrapper (a GPU, a port, a service) inside the lock too, with a bounded wait, because a gate before the lock lets a holder that retakes the lock starve the queue. A check started by a check runs at once. Test the wrapper before launch: a real check passes through it, and with `HERDSMAN_PROBES=off` and no reading it runs under the lock only and says so. A contract never names a wrapper that is not on disk; an agent that finds it missing stops and reports, and never runs a check without it.
- The lock belongs to an open file that the check and its children inherit, so the kernel frees it when the last of them exits, also after a `kill -9`, and never leaves a stale lock. A process that a check leaves running (a test server, a watcher) keeps the lock: the next check prints `run-check: waiting for the machine lock, held by pid <pids>`. Stop that process; the contracts already tell agents to stop their servers. When the holder is a job of another session (it holds the machine lock or the GPU), do not stop it and do not edit its scripts. Find the holders (`ps`), read their schedule, tell each agent the expected wait, and move the due times, because a cancelled wait ends the check as not run and makes reports late for a reason that is not the agent's. A "no writes" flag during that wait is expected ([`watchers.md`](watchers.md)).
- `agent-status.sh` prints the machine's 5-minute load against its core count and its free memory, and flags a load above the core count or under 10% free memory; the waiter reports a new flag as HEALTH. On a machine flag, start no new heavy work until it clears.
- "Not run" is the wrapper's own `run-check: NOT RUN` line (no lock within the wait, or the load gate gave up, each with its own reason line before it): a gap (implementer) or NOT CHECKED (reviewer). An exit code alone never says so: a check that started and then exited 75 is a failure like any other.
- Set the load limit from the machine's idle load, read before the route starts. Operating-system background work (media indexing, the window server, a container runtime's virtual machine) can hold the load over a fixed limit while no check runs, and every gate then waits for nothing. Every prompt caps that wait: a check that waits on the load gate for more than about ten minutes is cancelled and reported as a gap (implementer) or under NOT CHECKED (reviewer). The exception is a wait on a known holder from another session (see the lock line above): the agent keeps that wait running, and the moved due time covers it. A re-review reuses an earlier check result only when nothing that check reads has changed: its files, everything they import (shared helpers, exported fixtures), its configuration, the lock file and the environment. An untouched consumer of a changed helper or fixture is not unchanged: run its checks again.
- A load gate must work inside every harness's sandbox. The Codex sandbox denies `sysctl` and `memory_pressure`, so a wrapper that waits on an empty reading hangs forever and the reviewer runs no gates. Run the publisher outside the sandbox, as a background shell of the orchestrator: `/bin/bash <skill>/scripts/run-check.sh --publish <hours>` writes the reading to `/tmp/herdsman-load` every 15 s and stops by itself after that many hours. The wrapper uses that file while it is fresh; with no reading at all, it runs under the lock alone and prints that. Write the publisher's stop time in the route file and restart it before the next job: after it stops, sandboxed agents run with no load gate. Test the wrapper with `HERDSMAN_PROBES=off` before any agent gets it.
- Agents that run full gates on one container at the same time can exhaust its shared memory. Run one full gate at a time, or let the reviewer run only the touched packages while the integrator gates. Every brief says: wait and run again after a recovery, never restart containers. The lock prevents parallel runs but not this limit: one full gate can still crash a container with a small shared-memory size that holds thousands of leftover test databases. Suites drop the databases they create; a cleanup or a bigger shared-memory size means a container restart, which is the user's go.
- Look for those leftover databases before the first gate of a route: read the test database's database count and its container's shared-memory use (for Postgres: `select count(*) from pg_database`, and `df -h /dev/shm` inside the container). When shared memory is full, every agent's database tests fail with "No space left on device". When the count is high, put the recreate question in the route interview. During a route, a reviewer reports such a failure as the shared-memory ENV case with its evidence, never on the error text alone ([`contracts.md`](contracts.md), reviewer Severity): the error does not prove that the change is not the cause, because a change can raise peak use or leave databases behind. The recreate is the user's go (see the line above). After it, tell every agent with a running check to run its database checks again once, and have the reviewer run the closing run; a failure on the fresh database, or a database count that grows over the run, makes the line a P0. Reason: full shared memory fails every agent's database tests at once, so each review reports the same false P0 until the database is recreated.
- Database tests that skip for no clear reason can come from a full System V shared-memory table (orphaned segments of crashed embedded databases): check `ipcs -m`, and give the cleanup command to the user.
- Starting a container runtime can also start other projects' containers with a restart policy. Report them; do not stop them.
- Every contract says: when your browser tests end, close your pages, stop the test browser if no other agent is in a browser test, stop your local servers, and list what you closed in the report. On each wake, look for test-browser processes of finished agents and ask their owners to close them. Reason: idle browsers and servers load the shared machine and the user's desktop.

## Tests that prove the product

- A suite that skips environment validation everywhere hides boot failures: require one test that starts the real entry point with only the documented settings.
- A test harness must not set up anything that the real job does not (a trusted-directory setting, an exported variable, a loaded `.env` file). Such a setup masks exactly the failure the job will hit. Reproduce the job's conditions instead: its user, the owner of its workspace, its empty environment.
- The local gate is not the CI gate: CI usually has no `.env` files and keeps the runner's default per-test and per-hook timeouts. Tests that start child processes pass locally only because the parent loaded a `.env` file. Before a push, run the touched suites again with a clean environment (`env -i PATH="$PATH" HOME="$HOME"` plus the runner's flag that skips `.env` files). Pass again, after `env -i`, every setting that the contract or CI names for the suites, such as the agent's own `TEST_DATABASE_URL`: drop the incidental local exports, not the required test configuration, or the rerun fails on a missing setting or reaches a fallback database.
- Opt-in live tests may skip in the normal suites, but a route whose goal needs the live path must run it ([`contracts.md`](contracts.md), Live tests).

## Facts, not guesses

- Timestamps come from `date`; route-state lines come from [`scripts/route-log.sh`](../scripts/route-log.sh).
- Test logs written outside the worktree make a working agent look idle; check that folder before calling it hung.
- Know the base's gate results before the first review: read the default branch's latest CI run, and have the reviewer run the gates on the base in its own worktree through `run-check.sh` as its first job, while the implementers start. The orchestrator never runs them itself ([`SKILL.md`](../SKILL.md), Agent types). Keep a short list of known flaky tests and failures that already exist on the default branch in the shared rules, with the command that reruns them, so that agents report them as unrelated instead of chasing them; add the reviewer's findings to that list as an amendment. Later, before a failure is called new, the reviewer runs it on the base. A failure from a stale build cache needs a forced rerun (turbo `--force`).
- A CI job that failed before any test ran (an image pull rate limit, "The job was not acquired by Runner", a billing or spending block, a job that never starts) is an infrastructure failure, not a code defect. Read the job log and the annotations first. Rerun only the failed jobs (`gh run rerun <id> --failed`), spaced apart, with the permission and the cap of the next line; record each run as "no test ran"; push no new commit for it, because a push only queues more jobs; and give the merge decision to the user ([`git-and-github.md`](git-and-github.md), Review bots). A lasting CI fix (for example an image mirror) is its own CI-only pull request, proven by a green job, with the owner's yes.
- CI flakes on a shared CI database (a different failing test per attempt, outside the pull request's files): rerun only the failed jobs, with explicit permission per attempt and the due time moved with it. Skip the rerun when the owner is about to push, because the push restarts CI. When the same test fails twice in a row, the owner runs that one file alone on the pull request's head before the next rerun; a blind rerun proves nothing new. Cap the reruns (about four): then report the pull request ready with the red job and every attempt listed, and the user decides. When one test fails on every rerun at one head but the previous head was green and the two differ by a file that cannot touch that test's data, the cause is likely the runner's schedule (one more test file shifts which suites run side by side), so reruns of the same head will not help: say so in the report.
- Compare the local toolchain versions with the versions CI pins, at launch. A lock file is changed only by the pinned package manager, never by hand and never by another version; lock-file drift in a report goes to the user as a question ("upgrade the pins?"). Put this rule in the shared rules: agents repeat the mistake when the rule lives only in memory.
- When an implementer's test results and the reviewer's differ, look for an environment difference first (exported variables, a loaded `.env` file, a different database). The accept decision rests on the reviewer's run, except for the two ENV cases ([`contracts.md`](contracts.md), reviewer Severity): the reviewer's own sandbox (denied sockets, shared-memory calls, loopback ports) while the implementer and the other reviewers pass on the same head, and a test database out of shared memory. Label those findings ENV, not P0, and the accept decision then rests on the case's closing run. Reason: a sandbox limit fails whole suites that pass elsewhere, and a false P0 costs a ruling and a review round. Compare the failure count with the other runs of the same head before you call many failures a product defect.
- A gate that exits 0 without running anything is a false green: a flag in the wrong position can print the tool's usage text and exit 0, a misspelled config key is ignored, tests can skip without a word, and a pipe into `tail` reports `tail`'s exit code. A report's test lines name what ran and what skipped (files, counts) and the command's own exit code; a line without them is a gap. Write the full output of a long check to a log file at a literal path and read the end of that file: a pipe into `tail` also drops the diagnostic dump that you need after a failure.
- `pgrep -f` matches the pane shell that carries the Herdr prompt text, because that text holds the process names. Remove the pane shell from the result, and say so in the report.
- A report that finishes much faster than the work should take is checked in the agent's own session transcript (the commands and their output) before you call it real or fake. Build caches can make full gates fast.
