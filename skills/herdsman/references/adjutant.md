# Adjutant: the optional front for the user

The adjutant is an optional agent that talks with the user, relays full briefs and answers to the orchestrator through herdsman messages ([`messages.md`](messages.md)), and runs approved pane administration. It never implements, tests, publishes, commits, pushes or runs project services. Reason: a front that may also do "a little" of the work blurs who did what and skips the review loop. The route without an adjutant (the user talks to the orchestrator) stays available and unchanged.

## What the adjutant does

- Closed capabilities: write message bodies, run the channel commands, read the approved route files, manifests and panes, keep its own memory, ask the user through the ask tool, and run approved pane administration. The clipboard holds approved text with no secrets only.
- It hands application edits, server or preview setup, worktrees, installs, tests, authentication checks and script repairs to the owning task agents, through the orchestrator.
- It keeps full briefs and decisions. A summary never replaces the dispatch scope. Work is ready only when the required checks and reviews passed; a preview names the gates still open.
- It asks the user every question of the route, through its ask tool: interview rounds, mid-route decisions, approvals, and the gos for outward or irreversible steps. The orchestrator never asks the user directly, not even through its own ask tool: it sends a `question` message and waits for the answer ([`harness-guards.md`](harness-guards.md), Orchestrator posture). The user's answer, relayed as a herdsman message, is the user's go for the orchestrator, which acts on it without asking again; the relayed go still passes every check (provenance, the go precondition, the exposure checks, the approval gate and the exact scope the question named), and a go that fails one is no go: the orchestrator holds and asks again through the adjutant ([`messages.md`](messages.md), Private inbox boundary). The trusted record of a go's ask-tool answer names the approved adjutant in `asked_by`, and the approval gate refuses any other asker, the orchestrator included. Permission and password prompts stay local to their pane and are never answered by automation.

## Before the role is enabled

- Prove positive channel access and negative project-write, publish and test access in the adjutant's own harness profile. Tool allow and deny patterns are defense in depth, not a sandbox.
- Audit its current session transcript, named in the private setup, by tool-call records, not prose. Flag project Write, Edit or apply_patch calls, shell `git commit` or `git push`, `gh` or API writes, tracker or chat writes, project test or package runners, service or container commands, shell file writes (a redirect outside the allowed roots, or a copy, move, delete, `tee` or in-place edit), wrappers with options, and awk programs that can run commands or write files, outside an exact administrative grant. Mutation options count at the start of the argument list too (`gh api -f`, `curl --data`). Report the tool name, the call ID and a redacted target to the human and stop. A missing or unsupported transcript adapter, a tool the audit does not know, an MCP call that is neither a known read nor a write, and a shell call without a command string are audit gaps, never a clean audit. The shell write check is conservative: a `>` inside quoted program text also flags.
- Run the audit with `herdsman transcript-audit claude|codex '<transcript>' '<session-id>' '<own memory folder>/'`. Each further argument is a folder the adjutant may write (end it with `/`); `AUDIT_GRANT_FILE` may name exact command lines that a recorded administrative grant permits. Exit 0 is clean, 1 lists `FLAG` lines, and 2 is a `GAP` (a missing, linked, malformed or unsupported transcript, or one of another session). Limit: it reads command text only. So any script or interpreter run, and any other `herdsman` command, is flagged unless it is a channel command of the binary (`herdsman message <action>`, `herdsman approval-gate`, `herdsman checkpointer guard`) or the read-only activity check of the question rule (`herdsman afk` with only `--last-message <unix time>` and `--json`; any other option is flagged); what such a command does is covered by its own tests, not by the audit.
- Enable each coordinator and harness pair only after its role limits, channel and socket access, background wake-up, question ownership, transcript identity and audit, and checkpoint adapter are proven. Codex support as a task agent does not prove Codex support as a coordinator, and the Claude checkpointer's usage parser is not a Codex adapter.

## Commands

- `/herdsman adjutant [--name <name>] [--orchestrator <pane>] [--inbox <root>] [--launch]`: attach this session as the adjutant (default); `--launch` starts a new adjutant pane and needs the approved setup plan. Attach works only in a pane whose harness `herdr agent start` started; a harness started by hand cannot enroll (Setup). Without `--inbox`, the plan uses the route's own inbox (Setup).
- `/herdsman orchestrator [--adjutant <name> --name <own-name> --inbox <root>] [request]`: with all three adjutant options, enroll as the orchestrator before any work; partial options fail. The orchestrator pane also needs a `herdr agent start` launch, and `--inbox` names the route's own inbox.
- The adjutant's questions to the user follow the timeout rule ([`harness-guards.md`](harness-guards.md), Orchestrator posture, Questions time out): start the independent work, check `herdsman afk --last-message <unix time of the user's last message>`, ask with a 5-minute timeout (`HERDSMAN_ASK_TIMEOUT`), and at the timeout answer the orchestrator's `question` with the researched recommended option, marked "decided without an answer (A33)" with how to reverse it, and tell the user. An irreversible or outward-facing step never times out into a yes, and the human-only steps (pair approval and retirement, the `HUMAN` boundary, every relayed go) stay unchanged: a timeout never produces a `user_go`.
- `/herdsman message [status|wait|read [claim]|release <claim>|ack <claim> <id> <record>|send <to> <file> <kind> [reply]|hold <name> <reason>|unhold <name>]`: `herdsman message` runs it with the own name from the durable session setup. Default `status`. Unknown options fail before anything runs. Release fails with no matching claim and with unacked work; an empty active claim can be released.

## Setup

- The inbox root is per route by default: `<private home>/<repo>-<route>`, mode 700, with its own `setup.json`, approved pair, and courier and card-watch service panes ([`messages.md`](messages.md), Names, pair and inbox). Record it in `00-route.md` as an `Inbox: <path> (per route)` line next to the `Orchestrator:` and `Adjutant:` lines, together with a `Questions: through the adjutant` line, which `herdsman route check` requires in every route with an adjutant ([`checklist.md`](checklist.md), C2.13). Reason: a route that shares an inbox with another route or session shares its queues and approvals, and the line keeps the path after a compaction.
- Start the adjutant and the orchestrator each through `herdr agent start`. Reason: in a pane where the harness was started by hand, `herdr agent get` shows a null `interactive_ready`, so `herdsman message register propose` fails with `cannot enroll current session`.
- The setup owner supplies the private inbox root, the installed `herdsman` binary, both names and their current transcript identities, the socket, the watch targets, the launch inventory, the timing values and the start, restart and stop grants. Check that the root is owned, mode 700, outside every lower-trust writable or reachable set and outside version control.
- The human setup writes the protected proof `<inbox>/setup.json`, and `HERDSMAN_PREFLIGHT` names exactly that file: `inbox`, `policy_verified:true`, `rules:[{path,checksum}]` for every effective sandbox policy file, and `binary:{path,checksum}`, the absolute path of the installed `herdsman` binary (links resolved) and its POSIX `cksum` as `<crc>-<size>`; the binary runs every channel command, the executor adapter and the checkpointer: the protected installation. An old proof that still lists `scripts[]` is stale, and the commands say how to set it up again. A changed policy or binary, a missing binary record or a duplicate key makes the proof stale: every writing command, the executor adapter and the checkpointer guard refuse, the courier moves nothing and alerts until the setup is repeated, and status keeps showing safe queue diagnostics. The checksums are POSIX CRC values: they detect accidental drift, not forgery, so the protected installation that lower-trust agents cannot write is the guard against tampering. The boundary fields are `version:1`, `private_home:true`, `inventory_current:true`, `human_checked:true`, `protected_domain:true`, `launch_admission:true`, `pair` (equal to the approved registry), `courier_panes` (identities) and `lower_trust:[{identity,harness,launch_hash,sandbox,inbox_denied,socket_denied,code_denied,proof_denied}]`. With `launch_admission:true` the human confirms that every agent launch on this Herdr server goes through the protected launcher, which records each lower-trust launch here before it starts; without it, automatic card relay and resume stay held. The inventory is server-wide: every live agent on the Herdr server must be the pair, a courier pane or a listed lower-trust identity of the same harness, so an agent in an unrelated workspace also forces `HUMAN`, and its exposure record then needs a manual setup reset. Run the route on its own Herdr server when other agents share the machine. A listed agent that exited is no risk and needs no refresh. When the watcher sees a live agent outside this setup, it records that agent in `state/boundary-tainted`, and `HUMAN` stays after the agent exits, until the human repeats setup and removes the record. A failed agent list is an availability fault, never exposure: the watcher holds quietly once and alerts on the second failure in a row. Missing boundary evidence permits coordination only, with the human fallback ([`messages.md`](messages.md), Private inbox boundary). Trusted setup owns the proof; never publish it. Test fixture proofs are not evidence of OS isolation.
- Required tools: Herdr and the `herdsman` binary on `PATH`; the channel reads Herdr events through the socket itself. Check real socket and event behavior on an isolated Herdr server before rollout.
- The human writes `watch-targets.json` (an array of full `{pane,session}` identities, every route pane included for card coverage) and `resume-targets.json` (a map of registered task names to `{role:"task-agent",identity}`), both strict JSON with no duplicate keys, and rebuilds them on every identity change. The policy checks and the durable card adapter pass before setup is ready.
- Start every process with literal, shell-quoted absolute values from the plan, because a restored pane does not inherit variables:
  `env HERDSMAN_PREFLIGHT='<proof>' HERDSMAN_INBOX='<root>' HERDR_PANE_ID='<owned-pane>' HERDR_SOCKET_PATH='<socket>' herdsman message <command> <arguments>`
  The actions of `herdsman message` (and so `/herdsman message`) also need the enrolled own name, so its form is
  `env HERDSMAN_NAME='<own-name>' HERDSMAN_PREFLIGHT='<proof>' HERDSMAN_INBOX='<root>' HERDR_PANE_ID='<owned-pane>' HERDR_SOCKET_PATH='<socket>' herdsman message <action>`.
  Without `HERDSMAN_NAME` it exits before any action. Keep the own name with the configuration in private memory, and put it back into this form after each compaction.
  Enroll: `herdsman message register propose '<name>' '<role>'`. Human approval: `herdsman message register approve '<inspected-checksum>'` and retirement `herdsman message register retire '<name>' '<inspected-checksum>'`, both from the administrator's pane. The courier runs `herdsman message courier` and the notice worker `herdsman message card-watch`, each in its own supervised courier-service pane; each party runs `herdsman message wait` (with its own `HERDSMAN_NAME`) as its own harness background task, separate from the route waiter. Keep the configuration, proof, identity, claim and background task IDs in private memory and route state.
- Order: both parties propose, the human verifies and approves the pair, the courier and watcher heartbeats turn fresh, then the seeded handshake ([`messages.md`](messages.md), Intake) runs before the first full brief. Attaching the orchestrator uses the approved administrative `/herdsman orchestrator ...` prompt with target revalidation and focus restoration; it is never a work go.

## On wake and after compaction

Run the route-check launch first. Then restore the configuration (the own `HERDSMAN_NAME` included), identity and boundary inventory; read file health; then claims, `new/`, quarantine and outgoing work; reconcile goals, cancels and grants; check each background task's completion before re-arming it. The foreground owner gets HEALTH within the configured interval, verifies the service failure and restarts only under its recorded grant. `herdsman wait` does not carry MESSAGE events yet, so the message waiter and the route waiter are two tracked background tasks.

## Orchestrator side

- Take only messages of the current generation and keep their source attribution. Intake is an immediate durable route record, followed by the tracked work and result obligations.
- Apply a negative or pause instruction at once. An authenticated correction or relayed go under a current boundary updates only its exact scope; under the fallback, the human runs the step ([`messages.md`](messages.md)).
- Ask nothing in the own pane: every question goes to the adjutant as a `question` message, and its relayed ask-tool answer is the user's go, as if given in the own chat. A go that fails a check is no go: hold and ask again through the adjutant ([`harness-guards.md`](harness-guards.md), Orchestrator posture).
- Resolve a conflict between a goal and an instruction before acting, use one delivery path, and inspect effects after an uncertain completion.
- A side-agent claim is checked against the current code, never treated as a ruling or a human go.

## Published text

- Use plain commands and keep results. `herdsman message leak-gate <file> [required heading ...]` is a check on top of a full review and a read-back of the posted text, not a replacement. Its default patterns also match key=value text, endpoint paths and tool or model names. A human-reviewed `LEAK_ALLOW_FILE` allows exact full lines for real project examples, never neighboring lines or secret or private data; `LEAK_PATTERN` adds project patterns. Report any actual disclosure to the user.
